Domains

Each domain maps to the part after @ in a user's login (e.g. contoso.com). Users authenticate with their own AD credentials — there is no stored service account for directory operations.

Audit logging

Each domain also has its own audit toggle in its edit form, which only matters while this is on.

Email alerts

Sends an email on failed logins and on account unlock / password reset actions. Any domain can override the recipients and/or SMTP server in its own edit form, or narrow which of these triggers apply to it.

Customize the subject and body of alert emails. A change saved here always takes priority. Otherwise, if a file exists in the template folder on disk (the templates directory), that's used. Falls back to a built-in default if neither is set.

Allowed login groups

Only members of one of these AD groups (direct or nested) may sign in to the portal. Defaults to Domain Admins.

NetBIOS domain name (optional)

AD's simple bind only recognizes a userPrincipalName or a DN directly - not an arbitrary email address. If this domain's users' email differs from their UPN, set the NetBIOS name (e.g. CONTOSO) here to enable a fallback sign-in attempt as CONTOSO\​sAMAccountName. Leave blank if email already equals UPN, which is true for most environments.

Email-attribute lookup account (optional)

Only needed when users' email address (the AD mail attribute) doesn't share a local part with their sAMAccountName or UPN - e.g. AD domain company.local, UPN user@company.local, email user@company.com. This account is used only to look up "which AD account has this email address" before sign-in; it is never used for searches, unlocks, or password resets afterward. A low-privilege domain account with default read access is normally sufficient - no special delegation required.
